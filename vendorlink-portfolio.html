VendorLink

A platform connecting event organisers with vendors through event listings, vendor applications, organiser decisions and post-approval payments.

Open live website ↗View GitHub repository ↗
01

Project Overview

Purpose, scope and recorded functionality.

01.1 Purpose and problem

The team developed VendorLink after seeing how difficult it was for vendors to find markets, expos and festivals in one place. The project set out to connect vendors and organisers through a shared platform for event listings, applications and decisions.

01.2 Core workflow

  1. I create an event and add a banner as an organiser.
  2. I find an event and apply for a stall as a vendor.
  3. I accept or decline an application as an organiser.
  4. After approval, I continue to PayFast when a fee applies.
  5. I check the payment status after confirmation as an organiser.

01.3 Technology and links

  • Source repository: VendorLink on GitHub
  • Application URL: vendorlink-1vla.onrender.com
  • Technology: Java 17, Spring Boot, PostgreSQL/Supabase, HTML, CSS, JavaScript, JWT and PayFast.

02.1 Stakeholder and collaboration

We presented the website idea and business model during Microsoft Teams meetings with the lecturer/WIL co-ordinator. We received verbal advice and a check of whether the application worked, but we did not keep written meeting notes. We used WhatsApp to communicate.

02.2 Working approach

The team reported a one-week sprint duration. No dated sprint plans, reviews or retrospectives were found in the repository history, so this portfolio records repository activity without assigning it to unverified sprint dates.

02.3 Reflection

Working as a two-person team with clearly separated roles meant that ownership of most tasks was obvious: Wazeer led the backend, database and integration work, while I concentrated on the frontend. This division suited our strengths and allowed us to work in parallel. However, our charter did not define how work would be handed over between the two layers, and this became visible when the frontend and backend had to be connected, with most of that integration effort concentrated around 1 October.

Our sessions with the lecturer/WIL co-ordinator gave us useful direction on the business model and confirmed that the application was working. Because we relied on verbal feedback and WhatsApp messages, however, we have no written record of the decisions made. In future I would add three simple agreements to the charter: record meeting outcomes in a shared document, define a “definition of done” that includes integration and testing, and agree on how branches are reviewed and merged.

03

User Stories and Tasks

US-01 · Create an event

Story: As an organiser, I want to create an event so vendors can discover it.

Acceptance criteria: Required details can be entered, valid information is saved, and validation errors are clear.

Tasks: Build event form; validate fields; save event; test valid and invalid submissions.

US-02 · Upload an event banner

Story: As an organiser, I want to upload a banner so the event listing is recognisable.

Acceptance criteria: An image can be selected and uploaded; successful upload is reflected in the event; errors are handled.

Tasks: Implement upload; connect storage or image URL handling; display image; test supported and invalid uploads.

US-03 · Browse event listings

Story: As a vendor, I want to browse events so I can find opportunities.

Acceptance criteria: Event information is readable and closed/full events are not presented as open application opportunities.

Tasks: Retrieve events; display cards/details; show availability; test empty and populated results.

US-04 · Apply to an event

Story: As a vendor, I want to apply to an open event so the organiser can consider me.

Acceptance criteria: Application is recorded for review; closed/full events reject applications; duplicate applications are prevented.

Tasks: Submit application; validate event status and capacity; prevent duplicates; expose application to organiser; test outcomes.

US-05 · Review an application

Story: As an organiser, I want to accept or decline applications so I can manage participation.

Acceptance criteria: The event owner can review applications; the status updates; unauthorised users cannot decide on another organiser's applications.

Tasks: Build review controls; check ownership; update status; handle capacity; test accept and decline paths.

US-06 · Pay after acceptance

Story: As an accepted vendor, I want to pay the stall fee so my registration can be completed.

Acceptance criteria: Payment is offered after approval when a fee is due; amount is correct; opening checkout alone does not mark an application paid.

Tasks: Connect approval to checkout; pass amount/reference; handle cancelled or failed checkout; test payment initiation.

US-07 · Confirm payment status

Story: As an organiser, I want to see whether a vendor has paid so event participation can be managed accurately.

Acceptance criteria: Confirmed successful payment updates the status; failed/cancelled payment is not shown as paid; organiser can view status.

Tasks: Handle payment confirmation; validate notifications; update stored status; display status; test success/failure.

US-08 · View application status

Story: As a vendor, I want to view my applications so I know whether they are pending, accepted or declined.

Acceptance criteria: Vendor sees their own applications and current status; status reflects the organiser's decision.

Tasks: Retrieve current user's applications; display statuses; verify access restrictions; test updates.

US-09 · Enforce account roles

Story: As a user, I want role-based access so restricted actions and information are protected.

Acceptance criteria: Protected actions require authentication; vendors cannot perform organiser-only actions; organisers cannot manage events they do not own.

Tasks: Review authentication/authorisation; test role restrictions; inspect error handling and secret exposure.

US-10 · Handle notifications and errors

Story: As a user, I want clear feedback when an application or payment changes or fails.

Acceptance criteria: Status is clear; relevant notifications appear where supported; errors do not appear as success.

Tasks: Review notifications; check messages; test transitions and failures; document gaps.

US-11 · Respect event capacity

Story: As an organiser, I want approvals to respect stall capacity so the event is not overbooked.

Acceptance criteria: Available capacity is checked; approval reserves capacity; a full event cannot exceed its limit; capacity release is handled correctly.

Tasks: Review capacity rules; test full events and repeated decisions; check cancellation behaviour.

US-12 · Recover from errors

Story: As a user, I want clear messages when an action fails so I know what to do next.

Acceptance criteria: Validation/server failures are not treated as success; messages are understandable; failures do not create incorrect application/payment state.

Tasks: Test validation, server/network failures and payment failures; log defects; retest fixes.

03.1 Reflection

Writing the work as user stories helped me think about VendorLink from the perspective of the two people who use it, the organiser and the vendor, rather than as a list of pages to build. As the frontend developer, I found that the stories translated naturally into screens: event creation, event listings, the stall application form, the vendor’s application list and the organiser’s review dialog.

The most useful stories were those with specific acceptance criteria. US-06, for example, stated that opening the PayFast checkout must not mark an application as paid, and the final stall-fee flow follows that rule by waiting for PayFast confirmation. Some stories, such as US-10 and US-12 on notifications and error handling, were broader and harder to verify because “clear feedback” is open to interpretation. I would refine these into smaller stories with measurable criteria, estimate them, and link each one to the commits and pull requests that delivered it so that progress could be traced.

04.1 Reflection

Looking at the backlog as it was reconstructed from the repository, the order of work broadly made sense: a prototype first, then the backend and database, followed by deployment, payments and finally refinements to event management and stall fees. Each stage built on the one before it.

The weakness is that the backlog was reconstructed after the fact rather than maintained throughout the project. Without a visible, prioritised list, it was harder to see what was still outstanding, and important items such as stall fees after approval and refund requests were only delivered on 23 October. The moves from MySQL to Supabase and from Netlify to Render also changed the scope mid-project. Next time I would keep the backlog on a shared board from the start, reprioritise it at the beginning of each sprint, and record scope changes like these as backlog items so that their impact is visible to the whole team.

05.1 Reflection

We agreed on one-week sprints, but the repository activity shows that our work did not follow a steady weekly rhythm. There were no commits between 18 August and 14 September, or between 8 and 18 October, while other weeks were very busy, with 31 commits in the week of 28 September and 22 in the week of 19 October. This pattern suggests that our work was driven by deadlines and integration problems rather than by sprint goals.

A gap in Git activity does not mean that no work took place, as planning and design also happened outside the repository. However, because we did not record sprint plans, reviews or retrospectives, there is no evidence to show it. I have learned that the value of a sprint comes from its ceremonies as much as its duration. A short written sprint goal and a brief retrospective each week would have spread the workload more evenly and helped us identify problems, such as deployment issues, much earlier.

07.1 Reflection

Compiling the Agile Logbook from the repository history was a valuable exercise because it showed me our project as an outside reviewer would see it. The commit links provide clear, verifiable evidence of when features were added and by whom, and the pull request record shows that much of the backend work was merged in a structured way.

The process also exposed gaps in our record-keeping. Some commits used the generic author name “Your Name”, the contributor for the Netlify and Render setup could not be identified, and commit messages did not always describe the change clearly. Because the logbook was compiled from the repository rather than kept up to date as we worked, I had to infer some context from the code changes themselves. In future I would update the logbook at the end of each sprint, ensure every team member uses consistent Git author settings, and write descriptive commit messages that reference the relevant user story.

08

Individual Reflection

My contribution

My main role on VendorLink was frontend development. I set up the repository on 17 August with the first static prototype and a README describing the problem, planned features and technology. On 30 September I restructured the frontend into shared layout, UI helper, data model, demo data and page script files, and added the vendor dashboard and legal pages. Later I added twelve local event images with updated sample data, updated the site footer, and compiled the Agile Logbook and this portfolio from the repository record.

What went well

Restructuring the frontend is the contribution I am most satisfied with. Separating the shared layout and helpers from page-specific scripts made the pages easier to maintain and simpler to connect to the backend API once those services were ready. Working alongside a backend developer also helped me understand how much the frontend depends on authentication, CORS configuration and consistent API responses, which were areas I had not dealt with in depth before this project.

What I would do differently

I would start integrating with the backend much earlier. The early prototype was built as static pages, and some of its initial image files did not contain usable image data, which led to rework later. Because integration happened late, a large number of fixes were concentrated around 1 October. I would also ensure there is only one copy of the frontend in the repository: keeping files in both the Frontend folder and the backend static folder meant that changes, such as the footer update, had to be made twice. Finally, I would commit smaller changes more regularly and route them through pull requests.

What I learned

This project showed me that Agile practices are only effective when they are applied consistently. Choosing a sprint length is easy; maintaining a visible backlog, recording decisions and reflecting regularly takes discipline. I also gained practical experience with Git branching and pull requests, deploying to Render, and working with a payment gateway in a sandbox environment. In my next project I will set up a task board in the first week, agree a definition of done with my team, and treat documentation as part of the work rather than something completed at the end.

09

Challenges and Lessons

Challenges visible in the project record.

Recorded challenge
Deployment and integration fixes clustered on 1 October, about six weeks after the repository was created.
Frontend files were kept in both the Frontend folder and the backend static folder.
Some commits used a generic author name, and one large frontend update went directly to main.
No dated sprint plans, reviews, retrospectives or task-board updates appear in the repository log.

09.1 Reflection

The challenges recorded in this project stem mostly from integration and process rather than from any single technical problem. Leaving deployment and integration until late meant that issues with CORS, authentication and API routes all surfaced at once, and the repeated Render deployment-failure notifications show how much time was spent stabilising the build. Deploying a simple end-to-end feature early in the project would have exposed these problems while they were still small.

Keeping two copies of the frontend created duplicate work and the risk that the versions would drift apart, while inconsistent Git author names reduced the traceability of our contributions. The absence of sprint documentation also made it harder to demonstrate our Agile process. The main lesson I take from these challenges is that small, consistent habits, such as early integration, a single source of truth for the code, a clear commit history and brief written sprint records, prevent problems that are much harder to fix later.
